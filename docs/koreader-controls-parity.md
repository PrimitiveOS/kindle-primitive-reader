# KOReader reading controls and Reader parity

The tables below record the original controls comparison. For subsequent work,
the [source inventory](koreader-source-inventory.md) maps each upstream module
and panel to its reading behavior. The [real-document verification](real-document-verification.md)
records results through the Kindle Documents picker separately from simulator tests.

Reference release is KOReader **v2026.07.1**, commit `9192014d8bd82a91dc1012473be0f238dedfdb54`. The inventory follows the tagged Lua source through menu construction, gesture dispatch, document configuration and rendering. The acceptance tests extend the [reading parity plan](reading-parity-plan.md) and [requirements](requirements.md). [Tagged release](https://github.com/koreader/koreader/releases/tag/v2026.07.1) · [KOReader user guide](https://koreader.rocks/user_guide/)

## Current reading workflows

This checklist covers reading behavior, not KOReader's extension architecture
or general utilities. Reader may implement a reading-specific workflow as a
native feature without adding a plug-in host. Contextual Wikipedia and
translation from selected or visible reading text remain in scope when the
reader confirms the request. Network book acquisition, remote sync, remote
annotation export, Wikipedia article-to-EPUB export, Terminal/shell, RSS/news,
HTTP inspector/server administration, patch management and unrelated utilities
are outside the goal. Device settings stay in Launcher.

Rows marked **excluded** in the source inventory or control matrix are closed
scope. They are retained only to explain the KOReader reference and do not count
as open work, a release gate, or a gap in the Reader parity checklist. Reading
features that KOReader happens to package as plug-ins remain eligible for
native implementation; the plug-in framework itself does not.

**Released** means present in published Reader 0.1.1 at `40f1f3fc3a8978039239dc5a449e1eeeeb03567e`. **In progress** means visible in the next worktree changes and awaiting integrated validation. **Open** means the equivalent still needs implementation or provider work. ## Bottom configuration inventory

The bottom panel takes structured definitions rather than treating every option as a menu page. `ConfigDialog:onConfigChoose` updates the option value, dispatches its event, reevaluates dependent choices, and repaints the panel. Some controls hide the overlay until a timer fires or the event handler calls back. A tab change repaints the combined old and new bounds, and closing uses a partial refresh. Press and hold can expose exact values, help or a default-setting control. `ReaderConfig` persists document options under separate reflow and fixed-page prefixes. `ReaderMenu:saveDocumentSettingsAsDefault` provides an explicit path for global defaults. Reflow changes that affect pagination preserve the source location and selection, even while page numbers change. Font gamma or a view overlay can repaint without changing glyph advances. ## Live actions, defaults and return paths

Keep draw state, editable settings and the durable location separate. A direct choice such as the current rotation or text alignment can render in place and leave the panel open. A change that paginates text or crops a complex PDF may show a progress state, update the document and reselect the same panel. Crop selection, typed input and font selection need their own focus and cancellation. Save the per-book setting only after the change succeeds. Offer a deliberate action when saving a preset or copying settings to other books. A selected choice, current-book value and global default need distinct indicators.
